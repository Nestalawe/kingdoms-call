# Tests

```sh
npm test                    # every test, by level (about 30 s)
npx playwright test         # the browser specs, in Chromium (about 20 s): see "Browser specs" below
npm run check               # the quick check of what this branch changes (about 20 s; the Stop hook runs it)
npm run ratchet             # the counts in ratchet.json: none may rise
npm run test:full           # bigger fuzz runs, and ten times the property tests' inputs (the nightly run, with a random seed)
npm run test:quarantine     # the quarantined harnesses below (expected to fail)
npm test -- -t fuzz         # only tests whose name matches "fuzz" (a regular expression)
npm test -- --project unit  # one level: static, unit, scenario, simulation or page
KC_JOBS=1 npm test          # one test at a time (default: up to one per core in each of two levels at once)
KC_SEED=123 npm test        # another seed (the default, 20261001, is set in vitest.config.mts)
KC_SEED=123 npm test -- -t "^concede$"   # repeat one failure exactly (same seed and sizes): the footer prints this
node tests/<name>.test.js   # one test script on its own (unseeded, its own default sizes)
npx playwright test -g "map"           # only browser specs whose name matches "map"
npx playwright show-trace test-results/<spec>/trace.zip   # step through a failed spec (kept on failure)
npm run balance             # the balance matrix: 60 seeded games, and every realm's report, against the baseline (about 40 s): see below
npm run balance:update      # rewrite the balance baselines, in the PR that changes play
npm run balance:report -- --base main --head <file>   # the balance report of a run (from npm run balance -- --out <file>) against main
npm run mutants -- <folder>  # score the mutant patches in <folder> (tools/mutants/run.ts): local only, never in CI (docs/ARCHITECTURE.md#tests)
```

`npm test` is [Vitest](https://vitest.dev) (`vitest.config.mts`, P1-01a). It has one project per level: `static`,
`unit`, `scenario`, `simulation` and `page` (the levels are [below](#the-tests)).

- **New tests** are TypeScript Vitest tests in `tests/<level>/`, e.g. `tests/page/deterministic-boot.test.ts`, or,
  for what only a real browser shows, browser specs in `tests/browser/` ([below](#browser-specs)). Types for the parts
  of `lib/` they use are in `lib/*.d.ts`.
- **The test scripts** (`*.test.js`, written before Vitest) are listed in `suite.ts`, each with its level; a script
  that checks at more than one level sits at its highest. `legacy.test.ts` runs each one as a Vitest test in its own
  Node process, with the same arguments and environment as before; it passes when the script exits 0, and a failure
  shows the end of its output. They become real Vitest tests over P1-14. To add or quarantine a script, edit
  `suite.ts`.
- **The same answer every time.** The run stops at once on any Node but `.nvmrc`'s (`setup/global.ts`). The time
  zone is UTC and the locale `en_US`. A test set to retry or repeat fails, and so does a `.only`. A test that logs with
  `console.error` or leaves a rejected promise unhandled fails, unless it says it expects that with
  `vi.spyOn(console, 'error')` (`setup/each.ts`).
- **Time limits sized to the work, never a retry.** Vitest stops a test after 5 s. A test that builds the site, builds
  a TypeScript program, runs a tool over the tree (knip, dependency-cruiser, ESLint) or reads every file of `src/` gets
  a limit from `lib/time-limits.ts`: an allowance for each piece of that work, about five times the longest it has
  taken on GitHub's runners (`timeLimitForTheWork({ siteBuilds: 3 })`). A property test gets one from its run count
  (`timeLimitForPropertyRuns(RUNS, 2.5)`), so `KC_FULL`'s ten times the runs get ten times the time. The static tests
  type in no limit of their own, and ESLint refuses a `retry`, `retries` or `repeats` in any test file (`harness`).
- **Failures say how to repeat them.** Under Vitest's report, a footer (`setup/reporter.ts`) prints the seed and,
  for each failed test, the command that repeats it.
- **Levels run side by side**, two at a time, slowest first; within a level, up to one test script per core. More
  at once only overloads the machine.
- **The quick check** (`npm run check`, `tools/check.ts`, P1-01b): the type check, ESLint and Prettier on the files
  this branch changes, the import rules over all of `src/` (`npm run lint:arch`, P1-13a), the ratchet, then the tests. When only TypeScript under `tests/` or `tools/` changed, it runs
  the tests that import those files (`vitest related`). Anything else (the site, a test script, `setup/`, a config,
  the docs) runs every level but page, because `vitest related` can't see what the test scripts load: each runs in
  its own process and reads `site/` (built from `src/`) by file name. Page and the browser specs run in CI. Claude Code runs the check before an agent
  finishes, and the type check, ESLint and Prettier after each edit (`.claude/settings.json`, `tools/hooks/`).
- **The ratchet** (`npm run ratchet`, `tools/ratchet.ts`): counts of `@ts-nocheck` (in two since P1-10b1:
  `tsNocheckEngineSide`, the engine's side of `src/`, and `tsNocheckUi`, every other file), `@ts-ignore` and
  `@ts-expect-error`, `eslint-disable`, allowlist entries (the HTML rule's reviewed exceptions, `HTML_EXCEPTIONS` in `eslint.config.js`), JavaScript files, quarantined
  tests, test files that load `lib/stub-db.js`, test files on the engine's `vm` loader, ESLint's suppressed findings
  (`eslintSuppressions`: the counts in `eslint-suppressions.json`, P1-13b; ESLint's warnings on `src/`,
  `eslintWarnings`, before it), the import rules' known violations (`knownArchitectureViolations`: the entries of
  `.dependency-cruiser-known-violations.json`) and what knip finds unused (`unusedCode`, both P1-13a) may not rise
  above `ratchet.json`. When one falls, lower it in the
  same PR (`npm run ratchet -- --update` only lowers). `harness` runs the same comparison, so `npm test` fails too.
- **In CI** (`.github/workflows/ci.yml`, P1-01c) each part runs in its own job, side by side, each building `site/` from
  `src/` first (P1-05): the static checks
  (type check, lint, the import rules, format, ratchet and the `static` level), `unit` and `scenario`, `simulation`, `page`, the browser
  specs, the balance matrix ([below](#the-balance-matrix)), and `db`. The job named `ci` passes only when all but `db` passed; `ci` and `db` are the required checks.

## Browser specs

`npx playwright test` is [Playwright Test](https://playwright.dev) (`playwright.config.ts`, P1-01c). It runs the
specs in `tests/browser/*.spec.ts` in Chromium: what only a real browser shows (layout, the requests a page makes, a
broken image's `onerror` really firing). They are not part of `npm test`.

- **The site is served from one folder, as deployed**, by `browser/server.ts` (`lib/boot.js`'s `serve`), which
  Playwright starts on port 4173: `site/`, or the copy in `KC_SITE` (`KC_SITE=/tmp/broken-site npx playwright test`).
  A server already on the port is never reused. Specs open pages by path (`page.goto('/kingdoms-call-gm-portal.html')`)
  and answer supabase-js with a stand-in (`routeExternal`, `lib/stub-db.js`'s `browserSource`).
- **The same answer every time**, as in Vitest: the Node check (`setup/global.ts`), the time zone and locale
  (`setup/fixed.mts`, in Node and in the browser), `KC_SEED` with the same default. No retries, and a `.only` fails
  the run. A failing spec keeps its trace in `test-results/` (in CI, the run's `playwright-traces` download).
- **Wait for what happens, never a fixed time.** ESLint makes `waitForTimeout` an error in the specs, as well as a
  focused or skipped spec (`eslint-plugin-playwright`). A spec waits for the page to finish starting
  (`browser/started.ts`: the last thing each page's own start-up does), and checks with `expect.poll` or web-first
  assertions, which retry until they pass or time out. Where a check is "it happens promptly", the poll's timeout is
  that time (`dispatches-badge`). Code a spec runs inside the page is passed as text when it uses the page's own
  globals, exactly as the test scripts had it.
- **The specs from the test scripts** (P1-01c) check what the scripts checked, no more and no less. Each script's
  checks became one spec's `expect`s; a fixed wait became a wait for the event it stood for. The hostile-name tests
  were split: the jsdom half stays a test script (`hostile-*.test.js`), the Chromium half is `hostile-names.spec.ts`,
  one test per page and mode.

## The balance matrix

`npm run balance` (`tools/balance/`, P1-02a) plays 60 seeded games in the GM portal and compares them, game by game,
with the committed baseline in `balance/baseline/`. It answers "did this engine change change anything, and how
much?". Then it plays them again with every realm's report (below). It isn't part of `npm test` or `npm run check`: it
takes about 40 s on 14 cores (20 s for the page's games, 17 s for every realm's report).

- **The games** (`tools/balance/matrix.ts`): 48 all-bot games (3 to 6 realms, each on its rung of the map ladder ×
  sea 20% or 50% × normal or hostile bots × 3 seeds, races and alignments rotating; up to 30 turns, which almost
  every game needs to reach the Reckoning) and 12 with a **scripted realm** (`tools/balance/scripted.ts`): one realm
  held by the runner, which writes its orders from the saved state each turn, with no randomness. It does what bots
  don't: war on its nearest neighbour, Encounter and Pursue in turn (the armed king is the chaser, so the chase meets
  battles), an armed hero pursuing any quarry in a province with an unresolved battle. Its report is hashed too: an
  all-bot game writes none. The run fails if a scripted case (Encounter, Pursue, a chase held by an unresolved
  battle) never happens.
- **The invariants after every turn** (`lib/invariants.ts`, P1-04b), as in `turn-fuzz`, and the **report-leak check**
  on the scripted realm's report (`lib/report-leaks.ts`, P1-04c): a breach fails the game with its turn, the check and
  what broke ([below](#how-the-tests-reach-the-site)). They only read: the games are identical with them and without.
  The invariants add about 11 ms a turn (about 13 s of work over set A, 1 s on 14 cores).
- **One fresh page per game** (`tools/balance/play.ts`), booted through `lib/boot.js` with an explicit `seed` and
  `now`, in manual turn mode, stopping at the Reckoning. Games run side by side, one worker process per core
  (`--jobs N` to change it). The results are identical one game at a time and many side by side, and on a second
  run.
- **Exact:** per game and turn, 12-character hashes (`tools/balance/hash.ts`) of the saved state without its prose,
  the prose on its own, the GM log's structure and its text, the telemetry, the scripted realm's report
  (structure and text apart; per section over the game), and **every write** the turn sends to the stand-in database
  (`writes`, P1-02c: `tools/balance/writes.ts`). That last one is every write and database function (`rpc`) in order,
  with its table, operation, filters, modifiers and payload, so a changed filter, a field dropped from the save's
  `meta` or two writes swapped show even when nothing in play changed. The recorder wraps the stand-in client's
  `from` and `rpc` before the page boots, and copies each write when its query runs. Reads aren't recorded. Left
  out: the stand-in database's ids and stamps, the build stamp, and clock readings (the pinned clock moves on at each
  reading). In the writes, the JSON held as a string (`game_state`, `turn_report`) is parsed first so this reaches
  inside, and words are left out as in the other play hashes. Recording adds about 1.5–2 s on 14 cores.
  A baseline from before a column was added reads with it not kept: never a difference, and `npm run balance`
  refuses to compare with it.
- **Statistics** (`tools/balance/stats.ts`), per game, from the telemetry and the GM log: battles (attacker win % by
  kind, terrain and the realm side's leading unit type; units lost), lairs by grade, heroes' deaths by how, spells by
  school, realms at turns 10 and 20 and at the end, items, titles, game length and how it ended, chases.
- **The noise rule** (`tools/balance/paired.ts`): the two runs paired by seed, each statistic's change with its 95%
  and 99% ranges from resampling whole games 2,000 times (fixed resampling seed): "clear change", "possible change",
  "within the noise" or "too few to tell". The overall answer looks only at the bot games' headline statistics, with
  the bar raised for their number. `balance/baseline/noise.json` is the same matrix on other seeds: against the
  baseline, the rule must say "no meaningful change" (`unit/balance-baseline.test.ts`).
- **Every realm's report** (`tools/balance/every-realm.ts`, P1-12a1; P1-12's Decision 1): the matrix hashes only the
  scripted realm's report, so a bot realm's report, and so most of what perception does, was never compared. The second
  half plays the same games again in the engine's bare `vm` (`lib/engine.ts`, one worker process per core), each the
  matrix's own game (the set-up, seed, scripted orders and the shell's work around a turn: `lib/matrix-game.ts`), with
  a report for every realm every turn, bots' too (`lib/scenario-in-the-vm.ts`'s `reportEveryRealm`: built from copies
  of the slot rows, after the turn is saved). It checks that each turn's saved state hashes as the page's did (the
  turns are untouched), runs the leak checks on every realm's report (the audience check among them, on the turn's
  events, recorded as they are emitted: `recordTheEvents`, P1-12b3), and hashes each report, play and words apart,
  against `balance/baseline/reports.json` (both sets: about 5,800 reports a set). A difference names the game, the
  first turn, the realms and the report sections. It reads `src/`, so with `KC_SITE` it isn't played: its fail-first
  proof is a planted copy of the branch. `--out FILE` writes its run beside FILE (`every-realm.json`), and the balance
  report says in one line whether every realm's report is identical to the base branch's.
- `KC_SITE` plays another copy of the site. `-- --set B` plays the noise set; `-- --only bots-03,scripted-01` plays
  some games; `-- --out <file>` writes the run in the baseline's form, e.g. to compare two runs.
- When a change is meant to change play, or a realm's report, `npm run balance:update` rewrites the baselines (both
  sets, and both sets of `reports.json`); commit them with it.
- **In CI** (the `balance` job in `ci.yml`, P1-02b; `ci` needs it). Its first step,
  `tools/balance/engine-paths.ts`, runs in plain Node before `npm ci`. It compares the commit with the one before: a
  pull request's base, or, in `deploy.yml`'s run on `main`, the commit before the push. If no **engine path** changed,
  the job ends there, in seconds. The engine paths are the GM portal and every script its page loads, the data file,
  `tools/balance/`, `tests/balance/`, the helpers in `lib/` that the balance code imports, and the tools the matrix
  runs on (`package-lock.json`, `.nvmrc`: a jsdom or Node bump can change the games). The helpers include those the
  helpers import (the every-realm half loads the engine through `lib/engine.ts`). The runner refuses to
  play if its page loads a file that isn't on the list. Otherwise the job plays set A, one game per core, and fails if
  any game differs from the committed baseline: commit the new baseline with a change that is meant to change play. A
  pull request labelled `refactor-only` fails at the first step if it changes `balance/baseline/` at all. CI plays
  only the branch: the base branch's figures are its committed baseline. Adding or removing a label runs CI again.
- **The balance report** (`tools/balance/report.ts`, `npm run balance:report`, P1-03a). On a pull request the
  `balance` job compares its games with the base branch's committed baseline, game by game, and writes the report CI
  posts as a comment (`.github/workflows/balance-report.yml`, run when CI finishes; it runs only the default branch's
  `tools/github/balance-comment.ts`, never the pull request's code). The report first names the **class of change**:
  - **no change:** every game identical (a pure refactor);
  - **wording only:** every game played out the same (the state, the log's structure, the telemetry, the results, the
    scripted realm's report structure), and only words differ (if the database writes changed too, it says so);
  - **writes only** (P1-02c): every game played out the same, in the same words, and only what the turns wrote to the
    database differs. Nothing in play changed; it lists the games and the first turn that wrote differently, and
    replays nothing. That's expected only of a change to how the game saves: P1-17's moves of these writes must come
    out "no change";
  - **a reshape:** at least 90% of the games played out differently (`RESHAPE_SHARE`), as when the order of the dice
    changes, counting the games still being played at the first turn any game differs (a change from turn 18 can't
    reach a game that ended at 15). Every game differs, so it's judged as a whole, by the strict overall answer, which
    must be "no meaningful change";
  - **a rule change:** fewer games played out differently, and the rest are identical. It's judged by where the
    changed games first differ and by every figure and slice beyond the noise, so a change confined to one slice
    still shows in the verdict.

  Then: where the changed games first played out differently (up to 12, replayed on both sides to their first
  differing turn: the base's side on a copy of its site from `git archive`, through `KC_SITE`), the figures that
  moved, biggest first, each with one fixed label (`tools/balance/labels.ts`), the slices that moved, and how sure
  each is. With no report (no engine path changed, or the job stopped first) the posting workflow says so in an
  earlier report's comment, and posts nothing on a pull request that never had one. It also warns (never blocking)
  while a pull request whose report isn't "no change" or "writes only" has no "What changes in play" section. A base
  baseline without a column is compared on the rest, and the report says what wasn't compared.
- **Named scenarios** (`npm run balance -- <scenario>`, `tools/balance/scenario.ts`, P1-03c). A scenario measures one
  rule's direct effect in one staged scene; the matrix measures the knock-on effects in whole games. Each is a file in
  `balance/scenarios/`: a scene staged through `lib/scenario.js`, its number of runs (400), and the figures it
  reports, named and labelled as the matrix's statistics. Run *n* plays on a fresh page with seed *n* and the matrix's
  clock, so the base's runs and the branch's pair by seed and the noise rule judges them. The base's side plays a copy
  of `main`'s site (`-- --base REF` for another; `git archive`, through `KC_SITE`), then this side plays this site
  (or `KC_SITE`'s), each with every core. The result is a table to paste into a pull request: each figure before and
  after with its own 95% range and the cases behind it, the change with its range and how sure it is, and the runs it
  changed in. `-- --runs N` plays fewer runs for a quick look. Not in CI or `npm test`: about 45 s a side on 14 cores.
  - `battle`: 6 Elite Yeoman Longbows (a Human realm) attack 6 Average Dwarven Guard (a Dwarven realm) in the hills,
    plain commanders on both sides, measured on the first clash: attacker win %, units lost on each side;
  - `lair`: a young hero (Melee 2, 20 HP, no items) searches the Weak lair in their home: cleared, fled, killed;
  - `encounter`: Encounter Character on an enemy hero in the same province, catch rolls by Spy level (0 or 3 each
    side, 100 runs each).

## How the tests reach the site

- **`lib/boot.js`** is the one way to load a page from `site/`, which the run builds from `src/` before any test
  (`setup/global.ts`, `npm run build`, Vite since P1-09d; not when `KC_SITE` names another copy). A test script run on
  its own reads `site/` as last built:
  - `readPage` returns the page ready for jsdom, which runs no module script and loads no stylesheet: its bundle
    (`assets/<page>.js`) as a classic script at the end of the body, `"use strict"` first (a module runs once the page
    is parsed, after the classic scripts, in strict mode); its stylesheet inline where its `<link>` was;
    `kc-config.js` and the staging footer inlined; the supabase-js tag removed. `pageFiles` names the files it read.
    In jsdom every top-level function and `var` of the bundle is on `window`, listed in `globals.ts` or not; in
    Chromium only what `globals.ts` puts there ([traps.md](../docs/traps.md#nothing-is-on-window-but-globalsts));
  - `bootJsdom` boots it in jsdom;
  - `serve` and `routeExternal` do the same for Chromium (Playwright): the pages are served from one
    folder, as deployed (`browser/server.ts`); `vendor/supabase-js-*.js` gets a stub and the fonts get nothing;
  - every stand-in database answers `rpc('kc_db_version')` with `DB_VERSION`, the newest migration in
    `supabase/migrations/`, so pages pass their database version guard (P0-34). `bootJsdom`'s
    `opts.dbVersion` sets another answer (an older version, `null` for a missing function, `'offline'`, or a
    list used in order) and `opts.dbCalls` records the page's database calls.
- **`lib/engine.ts`** (P1-18c) is the one way to load the engine in Node: `loadEngine({seed})` runs the engine's
  bundle (P1-09d: Vite's build of an entry that re-exports the data file and every file under `src/engine/` and
  `src/views/`, in the GM page's order, `tools/pages.ts`'s `engineEntryFiles`) in a bare `vm` context with nothing but
  the seed and `console`, and returns the context, where the bundle's top-level names are the globals. It reads
  `src/`, not the built site (`src` names another copy, built again whenever the copy changes). The run builds this
  checkout's bundle once (`setup/global.ts`, into `node_modules/.cache/kc/`, its path in `KC_ENGINE_BUNDLE`); another
  copy's is built the first time a process asks (about a second). P1-14 moves the tests to importing the engine's
  modules ("The engine's modules", next); until then the ratchet counts the test files on the loader
  (`vmLoaderTests`), which only falls.
  There the turn is `resolveTurn` (`src/engine/run-turn.ts`, P1-18d): give it the saved state (JSON), the slot rows
  and the turn, and it returns the new state, the GM's log, the Spy-stealth step and `whatTheReportsRead`, which the
  shell calls in that order after the save (P1-12b2), then hands what the second returns to the views' `buildReports`
  (P1-12b3; in the same bundle; `unit/engine-purity.test.ts` plays a whole game this way). `runTurn`, the shell that loads, saves and writes the reports, is the page's. To play a turn on
  chosen dice, set them with `kcRng.use` around the call and give no seed; given a seed (as the shell gives one,
  P1-08m), the turn and its Spy stealth play on the seed's dice and draw nothing from yours, and the reports draw none. A helper lifted out of
  `resolveTurn` (P1-08) is a top-level function there: `engineFn(engine, name)` hands it back, and
  `turnContext(engine, state)` makes the turn's context it takes first, on a world parsed inside the `vm`, as
  `resolveTurn` holds it before the first phase (P1-08a), with everything `resolveTurn` adds to it made empty (the
  movement pools, the collectors, the battle count, the held-back skill rises, …). To see every call a helper makes to
  another top-level function, wrap it in the `vm` (`unit/xp-naval-passenger.test.ts` records each experience roll so,
  P1-08c). `botWorld(engine, realms, size, opts)` makes a new world of bot realms there, as
  JSON, and `quietEngineLog(engine)` quiets the line `emit` echoes to the console (P1-08b).
  **`lib/matrix-game.ts`** sets up one game of the balance matrix (`scripted-05`) for it: `newWorld(engine)` and the
  slot rows for a turn (`slotRows`, or `slotRowsJson` for a page's database), shared by `engine-purity` and
  `turn-shell`'s same-result test. **`lib/middle-of-a-bot-world.ts`** (P1-08i3) stages a case for a lifted helper on the
  middle of a bot world, cleared (open plain, nobody there; realms 0 and 1 at war, 0 and 2 allied): `board()` makes the
  context, `hero()` stands a hero there with troops and points of movement, `withDice` and `firstDie` pin the dice.
  `playTurn` (P1-08j1) plays a whole turn from the board; its third argument (P1-08j3) adds orders a realm sends under a
  key of its own (`hired_<hero>_via_<hirer>_ph<phase>`, written for a hero it means to hire). The board leaves the
  realms as the bot world dealt them, and they differ from seed to seed (creed, folk, starting discoveries, treasury,
  home): a case that leans on any of them stages it (`plainRealms` in `lib/recruit-hire-and-realm-works-order-cases.ts`
  makes them all plain).
- **The engine's modules** (P1-14a): how a new test, or one moved off the loader,
  reaches the engine.
  - It **imports the functions it calls from their modules**, typed (`import { generateNewGame } from
    '../../src/engine/world/generate.ts'`), and **imports `lib/the-whole-engine.ts` first**: it imports `run-turn.ts`,
    `world/generate.ts` and `clock.ts`, so every file has run its load-time set-up (as `engine/items/equipment.ts`
    re-tiers two of the content's tables), as in the bundle and on the GM page
    ([traps.md](../docs/traps.md#a-test-on-the-engines-modules-loads-the-whole-engine-first)). `unit/engine-loads`
    checks that every export then holds what the bundle holds.
  - **Fresh modules for a test whose outcome depends on the dice:** it calls `vi.resetModules()` and imports what it
    needs (`await import(…)`, still typed) before it seeds the dice (`kcRng.seed(…)`), so its world doesn't depend on
    the tests before it and `-t "<name>"` repeats it. A file of tests on tables and pure functions imports statically
    (Vitest gives each file fresh modules).
  - **A stand-in is `vi.spyOn` on the module that exports the function** (`restoreMocks` puts it back after each
    test). It reaches calls from other files only, so the test shows its stand-in is reached; a function called
    inside its own file is staged around (the state, or `kcRng.use`), not stood in
    ([traps.md](../docs/traps.md#a-stand-in-on-a-module-reaches-calls-from-other-files-only)).
  - **A variant of the engine's code** is a planted copy (`plantedSrc`, below) imported directly: `await
    import(path.join(copy.dir, '…'))`, after `importTheWholeEngineFrom(copy.dir)`. Its modules are its own, beside this
    checkout's.
  - **Its fail-first proof is a planted copy of the branch**, not `KC_SITE`: these tests read `src/`, as the loader
    does. Copy the branch, plant the fault in the copy's `src/`, and run the test there.
  - **`lib/a-staged-turn-on-the-engines-modules.ts`** plays one real turn on a small staged world on the modules:
    the same staging and results as `lib/scenario-in-the-vm.ts`'s `turn()` and `play()` (`S`, `S2`, `log`,
    `reports`, `collected`, `text`, `extra`, `reportEveryRealm()`), with no `W`: its `prepare(S)` calls what it needs
    from the modules, and a test stands a function in by `vi.spyOn`. Each call gives fresh modules, the dice seeded as
    asked (`scenario/battlefield-surgery-lines-sit-inside-the-battle` seeds them from `KC_SEED`).
